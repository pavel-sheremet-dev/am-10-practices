## Завдання 1. Агент обліку офісного обладнання

### Ситуація

В офісі є спільні речі: проєктор, кілька ноутбуків, мікрофон, подовжувачі, ключі від переговорок. Хто що взяв — у кращому разі написано десь у чаті, а частіше ніде. Через місяць ніхто не пам'ятає, у кого проєктор.

Робимо помічника в Telegram. Написати йому «що зараз видано?» — і отримати список. «Видай проєктор Андрію» — і запис оновиться. «Андрій повернув проєктор» — і обладнання знову доступне.

Ключова відмінність від усього, що ми робили досі: **немає заздалегідь прописаного маршруту**. Агент сам читає повідомлення, сам обирає інструмент і сам вирішує, з якими параметрами його викликати.

**Модель даних.** Один рядок таблиці — **одна одиниця обладнання**, а не одна видача:

- `is_returned = true` — обладнання **доступне**, лежить на місці;
- `is_returned = false` — обладнання **видане**, у полі `person` записано кому.

**Що будуємо:**

```
Data Table `equipment`
  item (String) | person (String) | is_returned (Boolean)

головний workflow   Telegram Trigger
                      → AI Agent  (+ OpenAI Chat Model, Simple Memory)
                      → Telegram (Send a text message)

                        інструменти агента:
                          ├─ Список обладнання
                          ├─ Додати обладнання
                          └─ Оновити статус обладнання

інструменти — окремі workflow, кожен із Execute Workflow Trigger:

  equipment-list    (use_filter, is_returned)
      → If (use_filter = false?)
            true  → Get Rows  без фільтра          (весь список)
            false → Get Rows  is_returned = <...>  (відфільтрований)

  equipment-add     (item)
      → Insert Row  item, person = "", is_returned = true

  equipment-update  (id, person, is_returned)
      → If (is_returned = true?)
            true  → Update Rows  is_returned = true             (повернення)
            false → Update Rows  is_returned = false, person    (видача)
```

**Назви workflow:**

- `equipment-control-agent`
- `equipment-list`
- `equipment-add`
- `equipment-update`

---

### Крок 1. Data Table `equipment`

**Що зробити.**

- Відкрити розділ **Data Tables**, split-кнопка справа вгорі → **Create Data table** → **Import CSV**, файл `practice-05-equipment.csv`. Структура таблиці і дані створяться з файлу.
- Назвати таблицю `equipment` і звірити типи колонок:

| Колонка | Тип | Що зберігає |
|---|---|---|
| `item` | String | назва обладнання |
| `person` | String | у кого воно зараз |
| `is_returned` | Boolean | `true` — доступне, `false` — видане |

- Якщо імпорту у вашій версії немає — створити таблицю руками і додати 5–6 рядків, частину з `is_returned = true`, частину з `false`.

**На що звернути увагу:**

- **`id` і часові штампи створення та оновлення з'являються автоматично** — їх не треба заводити й не можна перейменувати. `id` знадобиться у третьому інструменті.
- **Таблиця тут — каталог, а не журнал.** Один рядок живе весь час, у нього лише перезаписується статус. Історія видач при цьому не зберігається: щоб знати, хто брав проєктор пів року тому, потрібна інша схема — окремий рядок на кожну видачу. Для нашої задачі каталог простіший і достатній.
- **У доступного обладнання `person` порожній.** Так само його заповнює інструмент додавання.
- Data Tables живуть **усередині n8n**: не треба ні Google-акаунта, ні credential, ні зовнішньої бази.

### Крок 2. Інструмент «Список обладнання»

**Що зробити.**

- Створити новий workflow `equipment-list`.
- Тригер — **Execute Workflow Trigger** (на канві нода називається **When Executed by Another Workflow**). Два вхідні параметри:
  - `use_filter` — boolean
  - `is_returned` — boolean
- Нода **If**: ліва частина `{{ $json.use_filter }}`, тип **Boolean**, операція **is false**.
- Гілка **true** → **Data Table → Get Rows**: таблиця `equipment`, без умов, **Return All**.
- Гілка **false** → **Data Table → Get Rows**: таблиця `equipment`, умова по `is_returned`, також **Return All**.
- Запустити з редактора на різних комбінаціях параметрів. **Publish**.

**На що звернути увагу:**

- **Навіщо два параметри, а не один.** Boolean має рівно два стани — ним не скажеш «байдуже». Якби параметр був лише `is_returned`, агент не мав би способу попросити весь список. `use_filter` — це і є винесений окремо третій стан.
- **Умова на If читається навиворіт.** Ми перевіряємо `use_filter` **is false**, тому гілка **true** означає «фільтр не застосовуємо, віддаємо все». Місце, де легко переплутати гілки при складанні.
- У виході має бути видно **`id`** кожного рядка. Саме через нього працюватиме третій інструмент.
- **Publish обов'язковий** — у списку доступних інструментів з'являються тільки опубліковані workflow із цим тригером.

---

### Крок 3. Інструмент «Додати обладнання»

**Що зробити.**

- Новий workflow `equipment-add`.
- **Execute Workflow Trigger** з одним вхідним параметром:
  - `item` — string
- Нода **Data Table → Insert Row**, таблиця `equipment`:
  - `item` — `{{ $json.item }}`
  - `person` — порожній рядок
  - `is_returned` — `true`
- Запінити тестові дані в тригері, виконати, перевірити таблицю. **Publish**.

**На що звернути увагу:**

- **Агент передає тільки назву.** `person` і `is_returned` виставляє сам інструмент: нова позиція в каталозі за визначенням нікому не видана. Все, що можна не віддавати моделі, — не віддаємо.
- **Додати обладнання і видати обладнання — різні дії.** Тут ми поповнюємо каталог новою річчю. Видача — це вже наступний інструмент, і він працює з наявним рядком.

---

### Крок 4. Інструмент «Оновити статус обладнання»

**Що зробити.**

- Новий workflow `equipment-update`.
- **Execute Workflow Trigger** із трьома вхідними параметрами:
  - `id` — number
  - `person` — string
  - `is_returned` — boolean
- Нода **Data Table → Update Rows**:
  - умова: `id` = `{{ $json.id }}`;
  - оновлюємо `is_returned` = `false` і `person` = `{{ $json.person }}`.
- Перевірити обидві гілки на тестових даних. **Publish**.

**На що звернути увагу:**

- **Звідки агент візьме `id`.** Користувач не знає ідентифікаторів — він скаже «видай проєктор Андрію». Тому і в системному промпті, і в описі інструмента буде окреме правило: **спочатку викликати список, знайти потрібний рядок, взяти з нього `id`, і лише потім оновлювати**.
- Це найчастіша точка відмови всієї конструкції — і в нашому завданні, і в домашньому. Варто перевірити її окремо.

### Крок 5. Агент у Telegram

**Що зробити.**

- Створити бота: у Telegram написати **@BotFather** → команда `/newbot` → отримати токен.
- У n8n створити credential **Telegram API** з цим токеном.
- Новий workflow `equipment-control-agent`:
  - **Telegram Trigger**, Updates — `message`.
  - **AI Agent**: Source for Prompt — **Define below**, у полі Text:
  - **Chat Model**.
  - **Simple Memory**: Session ID → **Custom Key**, значення:
  - **Telegram → Send a text message**: Chat ID — той самий вираз, Text — `{{ $json.output }}`, у Options **Parse Mode: HTML** і **Append Attribution** вимкнути.
- Написати **системний промпт**. Що в ньому має бути:
  - роль — помічник для обліку спільного офісного обладнання;
  - перелік трьох інструментів їхніми людськими назвами;
  - правило про `id`: перед видачею чи поверненням спочатку отримати список і знайти в ньому запис;
  - правило про неоднозначність: якщо підходить кілька записів — уточнити, а не вгадувати;
  - заборона вигадувати назви, людей, статуси та `id`;
  - формат відповіді: HTML для Telegram, без `<br>`, нумеровані списки, повний список розділяти на «Видане» і «Доступне», технічні поля не показувати.
- Додати три інструменти через **Execute Workflow (Call Another Workflow as Tool)**. Для кожного:
  - обрати потрібний workflow зі списку;
  - написати **опис**, перший рядок якого — `Назва: ...` (саме ця назва фігурує в системному промпті);
  - біля кожного параметра натиснути **AI Magic**.

**На що звернути увагу:**

- **Назва інструмента живе в описі, а не в назві ноди.** Ноди на канві називаються як workflow (`equipment-list`), а агент читає опис, перший рядок якого — «Назва: Список обладнання». Так системний промпт і описи говорять однією мовою, і водночас на канві видно, який саме workflow викликається.
- **Опис інструмента — не коментар, а частина промпту.** Агент обирає інструмент саме за описом, і туди ж виносяться значення параметрів: що означає `use_filter = false`, що означає `is_returned = true`.
- **AI Magic** біля параметра підставляє вираз `$fromAI(...)` — саме він дозволяє моделі заповнити значення. Без нього параметр лишається порожнім або статичним, і інструмент отримає не те, що сказав користувач.
- **Маршрутизація живе у промпті, а не в нодах.** Якщо агент плутає інструменти — правимо промпт і описи, а не додаємо Switch. Це принципово інший спосіб керувати логікою, ніж усе, що ми робили в модулях 3 і 4.
