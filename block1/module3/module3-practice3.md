## Завдання 1. Обробка вернень у n8n

### Ситуація

Той самий сервіс «Смачно», ті самі 300 звернень на день. Промпт у нас уже є, запит ми вже вміємо збирати. Сьогодні складаємо workflow, який робить це сам і додатково вирішує, у який відділ віддати кожне звернення.

**Що будуємо:**

```
Manual Trigger
  → Edit Fields        (текст звернення — імітуємо вхідні дані)
  → HTTP Request       (POST до OpenRouter, тіло з Expression)
  → Edit Fields        (дістати topic із відповіді моделі)
  → Switch             (5 гілок по topic + Fallback)
  → Edit Fields × 6    (у який відділ поїхало)
```

**Тестові звернення** — беремо з першої зустрічі. Для роботи достатньо трьох-чотирьох:

```
1. З картки списалось двічі за одне замовлення, 480 грн. Поверніть гроші!
2. Замовив о 18:30, зараз 20:15, статус досі «готується». Де їжа?
3. Суші були несвіжі, риба з дивним запахом. Викинув усе.
4. Доброго дня, а ви працюєте в неділю?
```

---

### Крок 1. Вхідні дані: Manual Trigger + Edit Fields

**Що зробити.**

- Створити новий workflow, назвати `smachno-requests-handler`.
- Додати **Manual Trigger** — запуск кнопкою прямо в редакторі.
- Додати **Edit Fields**, режим ручного маплення. Створити поле `ticket` типу String зі значенням першого тестового звернення.
- Виконати workflow і подивитись на вихід ноди: `{ "ticket": "..." }`.

**На що звернути увагу:**

- Edit Fields тут — **імітація вхідних даних**. У бойовому workflow на цьому місці стояв би Telegram Trigger або Gmail Trigger. Ми підставляємо тестові дані руками, щоб під час налагодження не залежати від зовнішніх подій. У Завданні 2 замінимо це на справжній тригер.
- Дані між нодами йдуть у **JSON** — тому саме формату ми приділяли час на минулій зустрічі. Кожна нода отримує JSON на вхід і віддає JSON на вихід.

---

### Крок 2. HTTP Request до OpenRouter

Нічого нового ми не вигадуємо — формуємо в n8n запит, який ви вже збирали в ReqBin.

**Що зробити.**

- Додати ноду **HTTP Request**.
- **Method:** POST
- **URL:**

```
https://openrouter.ai/api/v1/chat/completions
```

- **Authentication:** Generic Credential Type → **Bearer Auth** → обрати створений credential.
- **Send Body:** увімкнути. **Body Content Type:** JSON. **Specify Body:** Using JSON.
- У тіло вставити той самий JSON, що був у ReqBin, але текст звернення замінити на Expression:

```
{
  "model": "назва_безкоштовної_моделі",
  "messages": [
    {
      "role": "user",
      "content": "...ваш промпт із першої зустрічі..."
    }
  ]
}
```

- Виконати і подивитись відповідь.

**На що звернути увагу:**

- Промпт усередині `content` має бути **екранований** так само, як на минулій зустрічі: переноси рядків як `\n`, лапки всередині як `\"`.
- Замість плейсхолдеру (`[текст_звернення]`) потрібно підставити звернення, взяте з попередньої ноди.
- Ключ ніде не видно. Він у credential, а не в заголовку — на відміну від ReqBin, де ми вставляли його руками.

**GПотенційні проблеми.** Якщо в тексті звернення трапиться подвійна лапка, підстановка зламає JSON і запит не піде. Це реальне обмеження такого підходу — і воно зникає в Кроці 5, коли переходимо на вбудовану ноду.

---

### Крок 3. Дістати результат із відповіді

**Що зробити.**

- Додати після HTTP Request ноду **Edit Fields**.
- Створити поле `topic` типу String і перетягнути значення з панелі результатів або вписати Expression:

```
{{ JSON.parse($json.choices[0].message.content).topic }}
```

- Так само створити поле `summary`:

```
{{ JSON.parse($json.choices[0].message.content).summary }}
```

**На що звернути увагу:**

- `choices[0].message.content` — той самий шлях, який ми розбирали в ReqBin. Тільки тепер його читає не людина, а нода.
- Тут є важливий нюанс: у `content` лежить **рядок**, усередині якого JSON. Модель повернула текст, а не структуру. `JSON.parse` перетворює цей рядок на об'єкт, з якого вже можна брати поля.

---

### Крок 4. Switch — маршрутизація по відділах

**Що зробити.**

- Додати ноду **Switch**, режим Rules.
- Значення для перевірки: `{{ $json.topic }}`
- Створити 5 виходів:

| Умова (`topic` дорівнює) | Куди |
|---|---|
| `оплата` | Фінанси |
| `доставка` | Логістика |
| `якість їжі` | Кухня |
| `замовлення` | Відділ замовлень |
| `інше` | Загальна лінія |

**На що звернути увагу:**

- Умови перевіряються **зверху вниз**, спрацьовує перша, що збіглась.
- **Fallback обов'язковий.** Без нього дані, які не підійшли під жодну умову, просто нікуди не підуть, і workflow тихо зупиниться.

---

### Крок 5. Те саме вбудованою нодою

**Що зробити.**

- Поруч, окремою гілкою від Edit Fields, додати **Basic LLM Chain** (або AI Agent) і підключити до нього **OpenRouter Chat Model**.
- Для Chat Model знадобиться окремий credential типу OpenRouter — ключ той самий, але тип інший, ніж Bearer Auth.
- У поле промпта вставити той самий текст, звернення підставити через `{{ $json.ticket }}`.
- Порівняти результат із HTTP Request.

**На що звернути увагу:**

- Екранування не потрібне: промпт вводиться у звичайне поле, тіло запиту n8n збирає сам. Проблема з лапками зникає.
- Модель обирається зі списку, а не вписується рядком.
- **Правило:** є вбудована нода — беріть її; HTTP Request потрібен тоді, коли вбудованої немає.
- Але тепер ви знаєте, що **всередині вбудованої ноди — той самий HTTP-запит**, який ви збирали руками.

---

### Додатково: Pin Data і Executions 

**Що зробити.**

- Відкрити **Executions** і подивитись історію запусків: які ноди спрацювали, які дані пройшли, де була помилка (якщо була).
- Виконати workflow, натиснути на ноду і поставити **Pin Data**.

**На що звернути увагу:**

- Pin Data економить час і ліміти: коли ви налагоджуєте Switch, немає сенсу щоразу дзвонити в модель.
- Не забудьте **зняти Pin Data** після налагодження — інакше workflow працюватиме зі старими даними.

## Завдання 2. Бот прийому замовлень

### Ситуація

«Смачно» хоче приймати замовлення в Telegram. Бот має зібрати від клієнта дві речі: **що замовляють** і **куди доставити**. Якщо чогось бракує — уточнити. Коли є все — підтвердити замовлення.

Це структурний аналог домашнього завдання: там бот-перекладач збирає **текст** і **мову**, тут — **страву** і **адресу**. Механіка та сама.

**Що будуємо:**

```
Telegram Trigger
  → Switch (/start | /help | Fallback)
      /start   → Telegram Send Message (привітання)
      /help    → Telegram Send Message (що вміє бот)
      Fallback → AI Agent ── Chat Model (OpenRouter)
                         └─ Simple Memory (Session ID = chat.id, вікно ≥ 6)
                  → Telegram Send Message
```

---

### Крок 1. Бот у BotFather і credentials

**Що зробити.**

- У Telegram знайти **@BotFather**, надіслати `/newbot`.
- Ввести назву бота, потім username — має бути унікальним і закінчуватись на `bot`.
- Скопіювати **токен**.
- У n8n: **Credentials → Create Credential → Telegram API** → вставити токен у Access Token → назвати credential іменем бота → Save.

---

### Крок 2. Telegram Trigger

**Що зробити.**

- Новий workflow, назвати `smachno-order-bot`.
- Додати **Telegram Trigger**, підключити credential, у Updates обрати `message`.
- Запустити прослуховування і написати боту будь-яке повідомлення.
- Подивитись вихід ноди — знайти `message.text` і `message.chat.id`.

**На що звернути увагу:**

- n8n сам зареєстрував webhook у Telegram. Не треба ні формувати запити до Telegram API, ні опитувати сервер — усе заховано всередині ноди.
- `message.chat.id` — ідентифікатор конкретного чату. Він знадобиться двічі: щоб відповісти саме цьому користувачу і щоб розділити пам'ять між користувачами.

---

### Крок 3. Switch на команди

**Що зробити.**

- Додати **Switch**, значення для перевірки: `{{ $json.message.text }}`
- Два виходи: `/start` і `/help`, плюс **Fallback Output → Extra Output** для всього іншого.
- На виходи `/start` і `/help` повісити **Telegram Send Message** із фіксованим текстом.
- Chat ID у цих нодах:

```
{{ $('Telegram Trigger').item.json.message.chat.id }}
```

- У кожній ноді Send Message вимкнути **Append Attribution**, щоб прибрати приписку «Sent with n8n».

**На що звернути увагу:**

- Тут уперше знадобилось звернення **до конкретної ноди за назвою**. `{{ $json }}` бере дані з попередньої ноди, а нам потрібен chat id із тригера, який стоїть раніше в ланцюжку.

---

### Крок 4. AI Agent, Chat Model і пам'ять

**Що зробити.**

- На гілку Fallback додати ноду **AI Agent**.
- Підключити до нього **Chat Model** — OpenRouter Chat Model із credential.
- Підключити **Simple Memory**:
  - **Session ID:** режим із власним ключем (Define below), значення:

```
{{ $('Telegram Trigger').item.json.message.chat.id }}
```

  - **Context Window Length:** 6 або більше.
- У полі промпта (User Message) агента:

```
{{ $('Telegram Trigger').item.json.message.text }}
```

**На що звернути увагу:**

- **Session ID за замовчуванням розрахований на Chat Trigger і з Telegram працює некоректно.** Якщо його не змінити, пам'ять стане спільною для всіх користувачів бота: один клієнт побачить контекст іншого. Це найчастіша помилка в цьому домашньому завданні.
- **Модель не має пам'яті** — це ми знаємо з другого модуля. Simple Memory просто зберігає останні N повідомлень і підкладає їх у кожен запит. Тобто вікно на 6 повідомлень — це ще й додаткові токени на кожному виклику. Пам'ять не безкоштовна.

---

### Крок 5. Промпт

Тут повертається промпт-інжиніринг із першої зустрічі. Логіку сценаріїв описуємо в системному промпті, а не будуємо гілками з If.

**Що зробити.** Напишіть System Message для агента. У ньому має бути:

- **роль і задача** — бот прийому замовлень «Смачно», збирає дві обов'язкові речі: що замовляють і адресу доставки;
- **вказівка дивитись на всю історію розмови**, а не лише на останнє повідомлення — клієнт міг назвати страву раніше, а адресу щойно;
- **три сценарії:**
  - є і страва, і адреса → підтвердити замовлення: перелічити страви, назвати адресу і попросити підтвердження;
  - немає страви → запитати, що клієнт бажає замовити, і не питати про адресу;
  - немає адреси → запитати, куди доставити, і не перепитувати про страву;
- **що робити з нерелевантним повідомленням** — коротко повернути розмову до замовлення;
- **пряма заборона вигадувати** страви, яких клієнт не називав, і підставляти адресу самостійно;
- **формат відповіді** — українською, дружньо, максимум 2-3 речення.

## Додатково. Error Workflow — сповіщення про помилки

Беремо, якщо лишається час. Якщо не встигнемо на зустрічі — зробіть самостійно: це друга частина домашнього завдання.

**Що зробити.**

1. Створити **новий окремий workflow**, назвати `smachno-error-handler`.
2. Додати ноду **Error Trigger**.
3. Додати **Telegram Send Message** — сповіщення собі:

```
Chat ID: ваш власний chat id
Text: Помилка у workflow: {{ $json.workflow.name }}
      {{ $json.execution.error.message }}
```

4. Зберегти workflow.
5. Відкрити основний workflow → **Settings → Error Workflow** → обрати `smachno-error-handler` → зберегти.
6. Зламати навмисно: зіпсувати Expression у ноді Send Message або від'єднати credential.
7. Написати боту в Telegram і дочекатись сповіщення про помилку.
